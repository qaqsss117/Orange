# UI-P0-003 Application Shell Evidence

- Date: 2026-07-28
- Host: Windows 11 amd64, in-app Chromium browser and Tauri WebView2 shell
- Slice status: `in_progress`

## Qualification Scope

This increment establishes the shared application shell, startup state,
authentication guard, login and registration forms, five protected routes,
logout confirmation, toast/status primitives, and a safe render error boundary.
It uses the existing strict native business commands and does not add a WebView
network client, credential storage, arbitrary native invocation, mobile command,
or capability.

The slice remains `in_progress`. The current capability is intentionally
desktop-only, the configured Control Plane is still a development service, the
formal `UI-G0-001`, `ARC-G0-002`, and `API-P0-002` dependencies are not all
complete, and Android/iOS handlers plus macOS/iOS runtime evidence are absent.

## Startup And Routing

`src/App.tsx` uses exact `react-router-dom@7.18.1` with `HashRouter`, preserving
WebView refresh and history behavior without server-side fallback routing. The
application initially renders only a startup status. Protected route content is
not mounted until `initialize_business` returns an `authenticated` session with
a public user profile. Signed-out and unverified sessions are routed to login;
an unverified token receives an explicit revalidation action and never exposes
account content.

Initialization failure displays fixed safe copy and a retry action. Successful
authentication updates the in-memory session before protected content is
mounted. Logout uses the existing native stop-before-secret-cleanup command;
only its parsed signed-out response removes account content.

## Authentication And Error Safety

`src/pages/AuthPage.tsx` reuses `parseLoginCommandRequest` and
`parseRegisterCommandRequest` before dispatch. It supplies explicit labels,
email/password autocomplete, password visibility, registration confirmation,
required/optional invite handling, maintenance lock, duplicate-submit lock,
field errors, and fixed service errors. A failed request preserves the form;
successful authentication clears password fields. Raw exceptions, stacks,
tokens, native request objects, and server-controlled error text are not
rendered or logged.

`src/ui/AsyncState.tsx` owns loading, empty, error, retry, toast, confirmation,
and ErrorBoundary behavior. The confirmation dialog traps Tab focus, focuses
Cancel initially, restores the opener, consumes Escape and popstate/back as a
dialog close, and leaves the route unchanged. Browser testing found and fixed a
delayed `history.back()` cleanup race that could close a rapidly reopened
dialog; cancellation now consumes the dialog history entry before unmount, and
non-history unmount synchronously removes only its marker. The ErrorBoundary
shows fixed recovery copy and never renders or logs the thrown value.

## Security Boundary

Production services call only the existing typed wrappers for
`initialize_business`, `login`, `register`, and `logout`. They do not use
`fetch`, browser storage, raw `invoke`, HTML injection, dynamic evaluation, or
console logging. The existing `desktop-business` capability remains limited to
Linux, macOS, and Windows and was not extended to Android or iOS.

Deterministic browser states are selected from a closed list only when
`import.meta.env.DEV` is true. Production builds ignore the `shell` query
parameter and default to native services. `scripts/security/check_ui_shell.py`
enforces these boundaries in frontend CI; nine mutation tests cover storage,
raw invocation, preview guarding, route guarding, dialog history behavior,
desktop-only capability, root error logging, and premature completion claims.

## Browser Verification

The in-app Chromium browser verified the following at its available 1280x720
viewport:

- authenticated dark home and five real navigation links;
- signed-out login, registration history/back, password visibility, preserved
  values after a fixed network error, and zero horizontal overflow;
- startup loading, startup failure/retry, maintenance, and unverified states;
- account logout confirmation, initial Cancel focus, Escape close, immediate
  reopen, browser Back close, unchanged account route, and opener focus restore;
- no browser warning or error messages across the tested states.

The login page occupied exactly the 1280x720 document with no overflow. The
authenticated home had no horizontal overflow and used a small expected
vertical scroll at this below-baseline desktop height. The in-app browser did
not expose a mobile viewport switch in this run, so no new mobile screenshot or
mobile runtime claim is made. The existing `UI-G0-001` five-viewport visual
matrix continues to qualify the shared home layout; real Android/iOS back,
keyboard, safe-area, and WebView evidence remains required.
